# Работа агентов

Этот процесс обязателен через корневой `AGENTS.md`. Он адаптирует цикл
spec → plan → tasks → implement → converge из `ai-slop-detector` к существующему
OpenSpec. Новый движок, Spec Kit и второй каталог спецификаций не нужны.
Это инструкции агентам, а не фоновый сервис: CI выполняет команды проверок,
но не запускает LLM-ревью и не доказывает выполнение процесса.

## 1. Определить объём

Прочитать запрос, `AGENTS.md`, затронутые исходники и существующую спецификацию.
Проверить `git status`, отделить чужие изменения. Зафиксировать ожидаемое поведение,
границы задачи и критерии готовности. Не читать целиком репозиторий, логи или `.env`.

Для документации, текста и локального рефакторинга без изменения поведения
достаточно краткого плана в текущем диалоге, проверки diff и подходящих проверок.
Для новой функции, изменения API/БД/платежей, нескольких подсистем или поведения
пользователя использовать существующий подходящий OpenSpec change либо создать
`openspec/changes/<change>/` с proposal, design, tasks и specs по принятой структуре.
Не выбирать посторонний change только потому, что он последний по времени.

В proposal описать проблему, результат и non-goals; в specs — наблюдаемые сценарии
успеха, ошибки и ограничения доступа; в design — решения, совместимость и риски;
в tasks — конкретные изменения и их проверку. Для новой структуры ориентироваться
на соседние change-файлы, не переписывать старые артефакты ради нового шаблона.
Уточнять только недостающие продуктовые решения; технические решения в согласованном
объёме принимать самостоятельно. Существующее разрешение пользователя сохраняется.

## 2. Проверить план до реализации

У каждого требования должен быть сценарий проверки, у каждой задачи — цель и
затрагиваемые файлы. Проверить зависимости задач и влияние на API, сохранённые
данные, права доступа и интерфейс. Противоречия исправить до зависимых изменений.
Не превращать ревью плана в дополнительный обязательный запрос разрешения.

## 3. Реализовать

Работать небольшими законченными частями. Для исправления ошибки сначала
воспроизвести её; добавить регрессионный тест, если ошибка относится к логике.
Проверять поведение, а не копию реализации. Для правки документации или косметики
не добавлять искусственные тесты. Не менять спеки, чтобы скрыть несоответствие кода.

Отмечать задачу выполненной после её проверки. Сборка не заменяет визуальную
проверку, а моки не доказывают работоспособность внешней интеграции.
Не ставить отметку выполнено рядом с неисполненной проверкой.

## 4. Роли и передача работы

Роли можно выполнять последовательными проходами одного агента. Отдельные
субагенты используются только по явному запросу пользователя или применимым
инструкциям; этот документ сам по себе не требует их запуска. Если делегирование
разрешено, параллелить только независимые задачи с разными файлами записи.

| Роль | Ответственность | Результат |
| --- | --- | --- |
| Координатор | Объём, зависимости, согласованность API, интеграция, итоговые проверки и Git | План и подтверждённый итог |
| Исполнитель | Только выделенные файлы и согласованный контракт | Изменения, проверки, оставшиеся вопросы |
| Ревьюер | Проверка фактического поведения и требований; без изменения кода в этом проходе | Находки с доказательствами или отсутствие находок с ограничениями |

При передаче указать цель, change/требования, разрешённые файлы, ограничения,
зависимости, команды проверки и критерий готовности. Ревьюеру передать также
базовый commit и фактический diff. Исполнитель возвращает список файлов, что
проверено и результат; неизвестное не выдаёт за успех. Только координатор
делает итоговые коммиты и push; исполнители не запускают деплой и не пишут
в общие файлы одновременно. Новые пользовательские задачи не создавать
для внутренних этапов работы без отдельного запроса.

## 5. Ревью и сверка с требованиями

После реализации пройти [чек-лист ревью](review.md). Разделять дефект и пожелание.
Для дефекта указать приоритет, файл/строку, сценарий воспроизведения, влияние
и требуемую проверку. Отсутствие инструмента или проверки — ограничение,
а не доказательство отсутствия проблемы. Одноагентный проход обозначать как
самопроверку, не называть независимым ревью.

Для OpenSpec change заполнить `review.md` по [шаблону](review-template.md):
сопоставить каждый критерий со свежим кодом и результатом проверки.
Классификация расхождений: `missing`, `partial`, `contradicts`, `unrequested`.
Проверять также уже отмеченные выполненными задачи — отметка не является доказательством.

Незакрытые требования дописать в конец tasks.md отдельным разделом `Convergence N`,
с новыми уникальными ID и ссылкой на исходное требование. Не перенумеровывать
существующие задачи и не добавлять дубликаты уже открытых пунктов. Если расхождений
нет, tasks.md не менять. Незапрошенные улучшения вынести в backlog, не расширять
ими текущую реализацию. Если найден непредусмотренный код, оценить его необходимость
и принадлежность текущему diff; чужие изменения не удалять.

Устранять найденные дефекты и повторять затронутые проверки до выполнения критериев.
Не гонять одинаковый цикл без изменений и новых доказательств. При внешнем блокере
зафиксировать причину и завершённую часть; не объявлять задачу готовой и не
коммитить её как успешную итерацию при обязательной непройденной проверке.

## 6. Проверки и выпуск

Следовать обязательным проверкам из `AGENTS.md`. `bun run check` объединяет
проверку типов сервера, изолированные тесты и сборки обоих frontend-приложений.
Во время работы запускать узкие проверки, перед завершением — нужный полный набор.
Только документация не требует сборки приложений.

Для UI проверить затронутые состояния в браузере по DESIGN.md, включая узкий экран,
загрузку, пустой результат, ошибку и клавиатуру, когда они относятся к изменению.
Если визуальная проверка недоступна, явно оставить её открытой. Для оптимизации
зафиксировать измерение до/после: размер бандла, число запросов, длительность или
другую метрику. Не заявлять ускорение на основании сокращения строк.

Обновить документацию и `.env.example`, если изменились публичное поведение или
конфигурация. Проверить diff и staged-файлы, затем выполнить последовательность
из `AGENTS.md`: функциональный коммит → русские release notes → отдельный коммит
release notes → push. Деплой выполняет внешний процесс. В финале сообщить результат,
проверки, ограничения и коммиты; не обещать мониторинг без запущенного механизма.
