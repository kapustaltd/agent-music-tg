# refine-miniapp-material-hierarchy — Design

## Baseline

Референс: мобильный экран 368×582, тёмная тема, экран создания плейлиста.

Оценка проблемности: **6/10**, где 0 — всё в порядке, 10 — интерфейс
непригоден. Функциональный сценарий читается и обложки задают музыкальный
контекст, но для ежедневного мобильного использования есть заметные проблемы
масштаба, типографики и состояния элементов.

Средняя оценка slop по пользовательскому screen-аудиту — **5.4/10**. Приоритет
работы: loading AI и магазин (8/10 и 7/10), затем главная и плеер. Поиск,
lyrics и библиотека уже ближе к живому музыкальному продукту.

## Typography baseline

Убрать доминирование `700/800`: ориентир — около 80% Regular/Medium, 15%
Semibold и 5% Bold.

| Роль | Размер / line-height | Вес |
|---|---|---:|
| Главный заголовок | 26–28 / 32px | 600–650 |
| Заголовок раздела | 17–18 / 22px | 600 |
| Название трека | 15–16 / 20px | 550–600 |
| Исполнитель / metadata | 13–14 / 18px | 400–450 |
| Навигация | 11–12px | 500 |
| Placeholder | 14–15px | 400 |

Не выделять отдельное слово в главном заголовке оранжевым: акцент оставить
действиям и состояниям.

продукту.

## Desktop audit baseline

На desktop эти экраны выглядят взрослее мобильной версии: левая навигация,
центральная рабочая область и правый player уже формируют нормальную композицию.
Средний desktop slop — примерно **3.5–4/10**.

| Экран | Slop | Наблюдение | Направление |
|---|---:|---|---|
| Уточнение запроса | 4.5/10 | Большая карточка содержит ещё несколько одинаковых rounded-полей; варианты похожи на disabled inputs | Убрать внешний card, оставить заголовок «Какой плейлист собрать?» и простые строки с `→` |
| Create | 5/10 | AI/Поиск и input выглядят как два независимых паттерна; headline слишком концептуальный | Один dominant action: `Подобрать`/`Поиск` над input или компактный режим внутри строки |
| Desktop player | 2/10 | Самый зрелый экран, но artwork чрезмерно велик, нет previous в controls | Уменьшить artwork на 10–15%, добавить elapsed/total time и previous; очередь оставить вторым уровнем |
| Desktop search | 3/10 | Много пустого места справа, selected result слишком коричнево-оранжевый | Ограничить content до 720–800px или использовать вторую колонку; selection сделать тонким tint/border |

## Desktop composition rules

- Сохранять модель `navigation rail → focused content → player`, но не растягивать
  рабочую область на весь экран без контента.
- Для поиска использовать `max-width: 720–800px` либо заполнять свободную
  область связанными результатами: альбомы, исполнители, related results,
  preview выбранного трека.
- Большая карточка допустима только для самостоятельного объекта (player,
  dialog, selected media); уточнение и результаты должны жить на фоне с
  пространством между группами.
- Для уточнения убрать приветственное дублирование. Оставить одну мысль:
  `Какой плейлист собрать?` и короткое пояснение `Выберите направление или
  опишите запрос`.
- Для Create не делать headline, mode-switch и input тремя одинаково сильными
  блоками: один должен быть dominant action.

## Accent and radius rules

Оранжевый — это action/state signal, а не декоративная тема. Оставить его для
primary play/CTA, active navigation, progress, focus и осмысленного like/state.
Не использовать его для обычного headline, каждой selected-card, всех иконок и
обычного loader одновременно.

Целевой radius ladder для нового desktop UI: большие контейнеры около `16px`,
input около `12px`, небольшие buttons около `10px`; pills только для chips и
tags. Базовый фон почти чёрный, поверхности отличаются примерно на 3–7%
яркости, borders остаются слабыми.

## Results / Playlist baseline

Это один из самых зрелых экранов: desktop и mobile уже ощущаются как реальный
музыкальный продукт, а не как AI-концепт. Desktop baseline — **2.5–3/10
slop**, mobile baseline — **2.5/10**. Здесь нужен refinement, а не глобальный
redesign.

### Что сохранить

- Сущность плейлиста читается сразу.
- Список треков без лишних карточек воспринимается как библиотека.
- Обложка → название → исполнитель → действия образуют понятную структуру.
- Оранжевый в основном работает как action/state.

### Точечные проблемы

- Технический label `ПЛЕЙЛИСТ` заменить на спокойный `Плейлист`, 12–13px / 500.
- H1 оставить крупным, но снизить вес до 600–650: ориентир 28–32px.
- На mobile проверить пропорцию header: обложка 112–128px либо layout
  `artwork слева → title справа`; маленькая обложка рядом с тяжёлым H1 создаёт
  промо-ощущение.
- Карандаш рядом с названием не должен постоянно шуметь: показывать на hover /
  focus или открывать rename по tap на название; альтернативно убрать в `⋯`.
- `+ Новый плейлист` вынести из конкретного Results screen в раздел «Музыка»,
  список плейлистов или меню.
- Сохранить единую иерархию верхних действий: либо `Сохранить / Поделиться /
  Скачать` как равные actions, либо явно подтвердить, что скачивание — единственная
  primary CTA. Не позволять большой оранжевой кнопке затмевать название.
- `Добавить треки` переименовать в `Добавить по описанию` или оставить с
  placeholder `Опишите, что добавить`; кнопку `+` уменьшить до 36–40px.
- В обычной строке трека не показывать heart у каждого элемента: оставить heart
  для saved/active состояния, остальные действия открыть через `⋯` или tap.
- На mobile развести mini-player и bottom navigation: либо полноширинный player
  над dock, либо 8–12px боковых отступов и ясный визуальный gap.
- Для playlist collage предпочесть одну осмысленную обложку или действительно
  разные 4 изображения; автоматический одинаковый collage выглядит fallback.

### Results typography

| Роль | Размер / line-height | Вес |
|---|---|---:|
| `Плейлист` | 12–13px | 500 |
| H1 | 28–32px | 600–650 |
| Track count | 14px | 400 |
| Section title | 20px | 600 |
| Track title | 15px / 20px | 550 |
| Artist | 13px / 18px | 400 |
| Navigation | 11–12px | 500 |

Главная цель — уменьшить количество «особых» состояний и жирных элементов, а
не добавлять новые декоративные эффекты.

## Решения

### D1. Поверхности и ритм

Сохранить тёмную спокойную основу и акцент, но убрать ощущение «капсула в
капсуле». Использовать 8dp-ритм для внешних отступов, 12–16px для обычных
контейнеров и 16–20px для главного поля ввода. Пилюли оставить только для
компактных чипов и явных переключателей; верхняя панель и нижняя навигация
должны читаться как Material surface/container, а не как декоративные pills.

### D2. Типографика и два алфавита

Не полагаться на имена `Super Grotesk`/`Space Grotesk` без поставляемых font
files. Выбрать одну гарнитуру с кириллицей и латиницей и закрепить её через
bundled `@font-face` либо надёжный system-first stack. Минимальный мобильный
набор: основной текст 16px, заголовок секции 16–18px, подпись 12–13px,
межстрочный интервал 1.35–1.5. Проверять пары вроде `Панк-рэп / DnB`,
`grustnaya muzyka`, `English mood`, длинные названия и смешанный текст.

### D3. Иконки

Использовать конкретно `@mui/icons-material`: это соответствует запросу на
Material UI, а не только на визуально похожие Material Symbols. Задать единый
mapping для поиска, AI, музыки, магазина, профиля и админки; не смешивать
Lucide и Material-иконки в одном экране. Визуальный glyph — 20–24px,
tappable icon-only control — минимум 44×44px. Filled/outlined варианты
использовать только для различения active/inactive или primary/secondary
состояния.

### D4. Motion и состояния

Для всех интерактивных элементов добавить единый pressed-state с переходом
140–180ms: изменение tonal background/color, лёгкий `translateY(1px)` и
`scale(.98)` только для визуального подтверждения нажатия, затем возврат к
исходному состоянию. Это должно работать на touch и pointer, не вызывать
layout shift и не зависеть только от hover. Для активного таба и AI/Поиск
добавить отдельное плавное изменение active container. Оставить явный
focus-visible. При `prefers-reduced-motion: reduce` переходы становятся
мгновенными.

### D5. Название плейлиста

Название должно быть вторичным результатом запроса, а не отдельным
литературным произведением: 2–5 слов, sentence case, без кавычек, эмодзи,
хэштегов и слов вроде «идеальный», «уникальный», «для твоей души». По
возможности сохранять язык запроса; для транслита допустима латиница, если это
естественное имя или пользовательский запрос. Если агент не дал имя,
использовать безопасный fallback из нормализованного запроса, а не английское
`Playlist`. Ручное переименование на экране результатов сохранить.

### D6. Бренд

Проверить знак примерно в диапазоне 24–28px, название 16–17px semibold и
высоту верхней панели около 52–56px. Увеличение должно освобождать бренд от
ощущения случайного watermark, но не превращать его в hero-заголовок.

### D7. Точный выбор технологии

На этапе реализации использовать `@mui/icons-material`, а не добавлять весь
`@mui/material`. Импортировать иконки точечно, без barrel-импортов, и после
миграции проверить размер miniapp bundle.

### D8. Product-first позиционирование

Контент и музыка должны быть визуальным центром интерфейса. AI не должен
выглядеть отдельным демонстрационным продуктом: loading, prompt и режимы — это
инструменты поиска музыки. На первом экране приоритетом являются запрос,
обложки и понятный следующий шаг.

### D9. Desktop density

Desktop не должен быть увеличенной копией Telegram Mini App. Контент получает
собственную max-width и ритм, пустая область либо исчезает за счёт более
сфокусированной колонки, либо заполняется связанным музыкальным контекстом.
Правый player остаётся постоянной зоной, но не должен конкурировать с
основным действием экрана.

### D10. Results refinement

Results screen считается отдельным refinement-потоком: не менять его рабочую
модель, а выровнять label/title/action hierarchy, сделать rename менее
навязчивым, убрать ошибочное место для `Новый плейлист`, уменьшить шум в track
rows и развести mini-player с bottom navigation на mobile.

## Риски

- Более крупная типографика уменьшит число видимых карточек; это приемлемо,
  если первый экран лучше объясняет действие и оставляет горизонтальный rail.
- `@mui/icons-material` увеличит bundle и потребует проверки tree-shaking;
  нельзя добавлять весь `@mui/material` только ради иконок.
- Ограничение названия на 2–5 слов не должно ломать имена альбомов и
  пользовательский ручной rename.
