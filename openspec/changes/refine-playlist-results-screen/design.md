# Design: refine-playlist-results-screen

## Контекст

`ResultsScreen` уже не показывает исходный запрос, поэтому проблема находится в
композиции самого результата и chrome приложения. На узком экране финальный
cascade в `anti-slop.css` превращает header в вертикальный блок с обложкой
120px, заголовком до 30px и отдельной строкой для primary «Скачать». В итоге
до списка треков доходит слишком мало viewport-height.

## Цели и не-цели

**Цели:**

- дать одну явную primary action для прослушивания;
- показать список треков раньше и уменьшить конкуренцию действий;
- сохранить доступность всех действий и стабильную геометрию состояний
  `idle` / `sending` / `sent` / `error`;
- не допустить overlap списка с фиксированными player/dock на мобильных ширинах;
- сохранить админский маршрут, но убрать служебный tab из основной навигации.

**Не-цели:**

- не добавлять новую зависимость или новый дизайн-компонент;
- не менять серверный контракт и обработку загрузок;
- не менять общий порядок треков и поведение проверки доступности.

## Решения

### D1. Прослушивание — главный сценарий

В `ResultsScreen` добавить кнопку `Слушать` с `Play`, которая запускает первый
доступный трек и передаёт в player очередь доступных треков текущего плейлиста.
Когда этот трек уже играет, кнопка показывает `Пауза` и использует существующий
toggle. Это повторяет уже знакомое поведение строк треков и не требует нового
API.

### D2. Скачивание — вторичное действие с ясным результатом

Кнопка скачивания остаётся доступной в том же action bar, но становится
вторичной иконкой. `aria-label` и `title` включают число треков: например,
`Скачать 10 треков в чат`. Это соответствует фактическому поведению
`api.download`: файлы доставляются в Telegram-чат поштучно, архив не создаётся.
Состояния отправки и успеха сохраняют тот же слот и не вызывают reflow.

Сохранение получает доступное имя `Сохранить в медиатеку` / `Убрать из
медиатеки`; визуально все вторичные действия имеют компактные touch targets
44×44px. Текстовые `span` сохраняются как доступный fallback, но не конкурируют
с primary action на экране.

### D3. Компактный mobile header

На ширине до 560px header использует две колонки: обложка 88px (80px на очень
узком экране) и copy справа. Название — 20–24px, `font-weight: 600`,
`line-height: 1.12`, `overflow-wrap: anywhere` и `text-wrap: balance`. Текст
названия получает отдельный flex/grid item, чтобы иконка переименования не
мешала переносу длинного имени.

На desktop сохраняется горизонтальный header с умеренной 104–120px обложкой.
Action bar остаётся одной строкой и не создаёт отдельную декоративную карточку.

### D4. Viewport reserve

Список и основной result content получают нижний reserve, учитывающий dock,
mini-player и safe area. Reserve находится после контента, а не между списком
и секцией «Добавить в плейлист», поэтому прокрутка остаётся естественной и
последний трек можно поднять выше fixed chrome.

### D5. Admin не является пользовательским tab

`BottomNav` показывает только пользовательские разделы. Для администратора
ссылка `Админ-панель` появляется в профиле рядом с помощью; переход остаётся
защищённым текущей проверкой `me.isAdmin` и серверной авторизацией. Экран admin
не получает новый публичный маршрут.

## Риски и компромиссы

- Иконка скачивания требует подсказки → сохраняем `title`, полное
  `aria-label` и явное количество треков.
- «Слушать» может начать первый трек, который ещё не прошёл проверку → берём
  первый трек из текущего `visibleTracks`; pending-треки остаются допустимыми до
  завершения существующего polling.
- Перенос admin в профиль добавляет один шаг для администратора → основной
  пользовательский dock становится чище, а доступ не исчезает.
