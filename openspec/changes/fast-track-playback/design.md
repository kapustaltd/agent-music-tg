## Context

Плеер использует активный `HTMLAudioElement`, а `/api/stream/:uri` проксирует progressive audio URL, полученный от `yt-dlp`. Первое разрешение URL — самый дорогой участок cold path. При смене `audio.src` браузер может асинхронно прислать `error` от прерванного старого запроса уже после того, как обработчик был переключён на новый трек.

## Decisions

1. **Общий cache yt-dlp.** Вынести `YTDLP_COMMON_ARGS` из extractor и использовать его в stream-resolver. Это сохраняет player-JS/nsig state между отдельными процессами `yt-dlp`, добавляет socket timeout и не меняет формат выбора progressive audio.
2. **Изоляция playback attempt.** Для каждого нового источника создаётся новый `HTMLAudioElement`, старый останавливается и отсоединяется. Дополнительно каждому назначению выдаётся monotonically increasing id и фиксируется нормализованный `audio.src`; обработчик ошибки/rejection делает retry только для активного элемента и актуальной попытки.
3. **Быстрый retry.** Задержка между ограниченными повторными попытками — 100 мс: достаточно уступить event loop браузера и завершить `src` transition, но не добавлять пользователю 800 мс искусственной паузы. Число попыток остаётся ограниченным двумя.
4. **Буферизация после клика.** Для dynamically assigned source используется `preload = "auto"`; это позволяет браузеру начать запрос сразу после назначения URL. Авторизация и server-side prewarm остаются без изменений.

## Risks / Trade-offs

- Общий cache занимает место в `data/.yt-dlp-cache`, но уже используется extractor и ограничен самим yt-dlp.
- Более быстрый retry может дать несколько коротких запросов на реально недоступный источник; лимит попыток остаётся прежним, а fallback на другой backend по-прежнему обрабатывается сервером.
- События браузера всё ещё best-effort зависят от WebView, но stale события больше не меняют состояние нового трека.
